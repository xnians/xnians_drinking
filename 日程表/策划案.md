## 1. 项目背景

### 1.1 问题：时间信息散、录入贵、遗忘成本高

大学生的日程来源高度碎片化：

- 课程群发的**截图**："实验报告第 13 周周五前提交"
- 教务处**通知图片**：一张图里塞了 5 个不同的截止时间
- 打印或手写的**课表照片**
- 口头约定、黑板通知、公众号推文

这些信息最终都躺在相册或聊天记录里。要用的时候得翻半天，翻到了还得手动抄进日历，抄的时候又容易漏掉"提前几天"这类隐含要求。

### 1.2 现有方式的不足

| 现有方式 | 卡在哪 |
| --- | --- |
| 手机自带日历 | 录入路径长（新建→选日期→选时间→填标题），一次录入 30 秒起 |
| 待办清单类 App | 擅长"要不要做"，不擅长"什么时候之前必须做完"，时间维度弱 |
| 微信收藏 / 相册截图 | 零成本收集，但零结构化，等于没收集 |
| 纸质笔记本 | 不可检索、不会提醒、跨天就忘 |

**缺口很明确**：从"一张图"到"一条带截止时间、按时排序的日程"，中间那段手工劳动没人替用户干。

### 1.3 目标用户

- **主用户**：在校本科生（自己 + 同班同学），每天要处理 3~8 个时间节点
- **典型画像**：有课表、有群通知、有实验报告 deadline，用 Windows 笔记本，不装额外软件
- **不服务的用户**：需要多人协同排期的团队、需要跨设备同步的重度日程用户（见 2.3 边界）

### 1.4 为什么值得做

这件事的价值不在"又一个待办清单"，而在**把最贵的那一步（录入）降到一次拖拽**。用户拍一张图，AI 把结构化信息抽出来，人只做"确认/改一下"，录入成本从 30 秒降到 3 秒。这是 AIGC 在这个场景里真正不可替代的位置。

## 2. 产品定位与目标

### 2.1 核心闭环（大赛硬要求）

```
用户上传图片
   ↓
多模态模型提取（标题 / 截止时间 / 隐含要求）
   ↓
结构化日程草稿（低置信度字段留空）
   ↓
人工确认或修正  ←—— 关键的人机分工点
   ↓
按规则进入分区列表（置顶待设时间 / 时间排序 / 不急 / 已完成）
   ↓
到点提醒 → 点圆圈打勾 → 移入已完成区并灰化
```

闭环的"结果输出"是**一条被正确分区、可被提醒、可被完成的日程**，不是一段识别文字。

### 2.2 两条录入路径并行

| 路径 | 输入 | 处理 | 适用场景 |
| --- | --- | --- | --- |
| 图片录入 | 截图 / 照片 / 课表 | 多模态模型 → JSON → 校验 → 草稿 | 信息已存在图里，重录入 |
| 手动录入 | 表单（标题 + 截止时间 + 备注） | 直接入库 | 临时想到的事、AI 识别失败的兜底 |

两条路径**写同一张表、走同一套分区规则**，不做成两个模块。

### 2.3 明确不做（本版边界）

- ❌ 多人协作、共享日历、任务指派
- ❌ 云同步与多端（本版数据只落本地 JSON）
- ❌ 复杂重复规则（"每周三"这种，先不做，理由：解析歧义大、收益低）
- ❌ 自然语言一句话建日程（本版只做图片 + 表单两个入口）

> 划掉这些不是能力不足，是**为了让"图片→日程"这一条路做到能用**。大赛评审看的是核心功能是否可体验，不是功能数量。

## 3. 典型使用场景

**场景 A｜实验报告截止**
群里发了一张通知截图，里面有"第 13 周周五 23:59 前提交实验报告，逾期扣 10 分"。用户把图拖进程序 → 识别出 1 条日程：标题"提交实验报告"、**截止时间留空但带原文"第 13 周周五 23:59"**、备注"逾期扣 10 分" → 用户确认 → 这条落入**待设时间区**并被橙色高亮盯着 → 用户点「设置时间」补成 12-04 23:59 → 它进入主列表正常排序，右侧显示"剩 11 天"。

**场景 B｜一张图多个时间点**
教务处通知图里同时有"报名截止 12/1""材料提交 12/8""答辩 12/15"。识别为 3 条独立日程，按时间自动排序。用户改掉其中一个识别错的日期，其余直接确认。

**场景 C｜识别不出时间**
手写课表照片，模型认出了"周三 3-4 节 大学物理"但没认出教室。时间字段缺失 → 这条自动落到**待设时间区**并高亮 → 用户补上教室和时间，它才进入正常排序。

**场景 D｜临时想到的事**
开会时突然想起"要去还书"，直接点"新增"，只填标题不填时间 → 同样进入**待设时间区**，被橙色提示盯着，直到补上时间。

## 4. 功能需求（核心）

### 4.1 录入

| 功能 | 行为描述 | 验收标准 |
| --- | --- | --- |
| 上传图片 | 支持点击选择 / 拖拽入窗；支持 png/jpg/jpeg/webp | 选完立即开始识别，界面显示"识别中"且按钮禁用 |
| 识别结果确认 | 弹出草稿卡片，字段可编辑；逐条可勾选采纳/丢弃 | 未确认前不写库；丢弃的条目不残留 |
| 手动新增 | 表单：标题（必填）、截止时间（**日历选择**，可空）、备注（可选）、不急（开关） | 标题为空时"保存"不可用；不选时间也能存，存完进「待设时间」区 |
| 编辑 | 任意条目双击进入编辑，字段同上 | 保存后列表立即按新规则重排 |
| 删除 | 右键或条目菜单删除，二次确认 | 删除后不占用任何分区计数 |

### 4.2 分区与排序规则（本项目的核心）

**存储只记 3 种状态**：`pending`（待办）、`someday`（不急）、`done`（已完成）。
**界面上的 5 种呈现由规则推导**，不额外存字段——这样"过期"不需要定时任务去刷状态，打开就算出来。

| 界面状态 | 判定条件 | 所在位置 | 视觉 | 可执行动作 |
| --- | --- | --- | --- | --- |
| 🔶 **待设时间** | `status=pending` 且 `due 为空` | 主列表**最顶部**，独立橙色区块 | 橙色左边条 + 浅橙底 + 呼吸闪烁 + 右侧「设置时间」按钮；若有 `due_hint` 则用小字显示原始描述（如"第13周周五"） | 设置时间 / 补备注 / 标记不急 |
| ⚪ **进行中** | `status=pending` 且 `due > now` | 主列表，按 `due` 升序 | 正常黑字，右侧"剩 N 天/小时" | 完成 / 不急 / 编辑 |
| 🔴 **已过期** | `status=pending` 且 `due ≤ now` | 仍在主列表原位（按 `due` 排序），**不单独设区**〔已定〕 | **整行红字 + 左侧红条**，时间后缀"已过期 N 小时" | 完成 / 改期 / 不急 / 删除 |
| 🔵 **不急** | `status=someday`（**只能由用户手动点标记，不做自动判断**〔已定〕） | 独立「不急」区（默认折叠，标题显示条数） | 蓝灰弱化，不显示倒计时 | 恢复为待办 / 完成 |
| ✅ **已完成** | `status=done` | 独立「已完成」区（默认折叠） | 灰色 + 删除线 + 60% 透明，不参与排序 | 撤销完成 / 删除 |

**排序细则**

1. 主列表顶部固定是「待设时间」区块，块内按创建时间**倒序**（最新录入的在最上）。
2. 待设时间区块上方有一条横幅：`⚠ 2 项未设截止时间，请尽快补充`，0 项时整条隐藏。
3. 有截止时间的条目（含已过期）**合并按 `due` 升序**排列，不把过期项单独抽出来——过期项留在原时间位置，靠红色和"已过期"字样提示，避免用户失去时间轴的连续感。（〔已定〕保持此方案，不设独立"已逾期"区）
4. 「不急」与「已完成」两个区在主列表下方，默认折叠，只露标题和条数。
5. 任何状态变更（设时间 / 改期 / 标记不急 / 完成）后**立即重排**，不允许手动刷新。
6. 分界线：`今天 / 明天 / 本周内 / 更早 / 更晚` 作为日期分组标题插入，只在有待办数据的组出现。

### 4.3 完成交互（打勾动画）

```
① 条目左侧常驻一个 18px 空心圆
② 鼠标悬停 → 圆圈描边变实、轻微放大到 20px
③ 点击 → 圆圈内快速填充主色（120ms）
④ 对勾从左上到右下画出（180ms，两段折线描边动画）
⑤ 整行从主列表移除（tkinter 没有控件透明度，真淡出做不了，用直接移除近似；若必须真淡出需换 PySide）
⑥ 同时追加到「已完成」区顶部，已完成区条数 +1 并有轻微高亮脉冲
```

- 全过程约 **500ms**，期间该行不可重复点击（防连点）
- 动画期间**不阻塞**其他条目操作（用 `after()` 调度，不用 `sleep`）
- 撤销完成：在已完成区点条目右侧「撤销」，恢复到原分区，**保留原截止时间**

### 4.4 提醒

| 规则 | 描述 |
| --- | --- |
| 触发时机 | 截止前 1 天 / 前 1 小时 / 到点整（三档可各自开关） |
| 呈现 | 窗口从屏幕右下角滑入的提醒卡片，列出即将到期条目；不抢焦点（温和模式） |
| 依据 | `due` 字段；`due 为空` 的条目不参与提醒，但计入顶部横幅的催促 |
| 过期后 | 不再提醒，改为在列表中标红；每天首次启动时汇总一次"你有 N 项已过期" |

### 4.5 设置项

| 设置 | 范围 | 默认 | 说明 |
| --- | --- | --- | --- |
| 提醒提前量 | 关 / 1 天 / 1 小时 / 到点 | 1 天 + 1 小时 | 多选 |
| 温和提醒 | 开 / 关 | 开 | 开=不抢焦点 |
| 开机自启 | 开 / 关 | 关 | 写注册表 Run 项 |
| 关闭即收托盘 | 开 / 关 | 开 | 沿用 `喝水提醒` 的托盘方案 |
| AI 接口地址 | 文本输入（人工填） | 空 | 兼容 OpenAI 格式的 Base URL |
| 模型名 | 文本输入（人工填） | `qwen-vl-max` | 可换成任意支持视觉输入的模型名 |
| API Key | 密码式输入（默认掩码显示） | 空 | 只存本地 `config.json`；不硬编码、不读环境变量 |
| 测试连接 | 按钮 | — | 发一次最小请求，通过后才允许用图片识别 |

## 5. 技术方案

### 5.1 技术栈选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| UI | **tkinter**（Canvas 手绘动画） | 官方自带、零依赖、单文件可分发；Canvas 足够做圆圈+对勾动画 |
| 图片处理 | Pillow（唯一外部依赖） | 缩放、纠偏、压缩后再送模型，省 token |
| 多模态解析 | **通义千问 qwen-vl-max**（备选 GLM-4V / 豆包视觉） | 中文通知截图识别强、国内网络稳定、有免费额度；接口层做成可替换 |
| 存储 | 本地 JSON（`data.json`） | 与 `喝水提醒` 的 `config.json` 一致的做法，无需数据库 |
| 网络 | `urllib.request`（标准库） | 避免额外依赖；只发一次 POST，不值得引 requests |

> 关键取舍：**能不用依赖就不用**。整个程序除 Pillow（图片压缩）外全走标准库，双击即用，符合"不装环境也能演示"的诉求。

### 5.2 分层架构

```
┌─────────────────────────────────────────────┐
│  UI 层  main_window / edit_dialog / reminder │
│         （只负责渲染与事件，不含业务判断）    │
├─────────────────────────────────────────────┤
│  规则层  rules.py                            │
│         bucket(item, now) → 5 种界面状态      │
│         sort_key(item) → 分区内排序键         │
├─────────────────────────────────────────────┤
│  解析层  parser.py                           │
│         image → 预处理 → 模型 → 校验 → 草稿   │
├─────────────────────────────────────────────┤
│  存储层  store.py                            │
│         data.json 读写、原子写入、损坏回滚    │
└─────────────────────────────────────────────┘
```

**为什么把规则单独抽一层**：分区规则是本产品的灵魂（4.2 那张表），把它写成纯函数，就能脱离 UI 单测——`bucket()` 传 10 组边界数据，断言输出，这是唯一能证明"排序真的对"的办法。

### 5.3 数据模型

```json
{
  "version": 1,
  "items": [
    {
      "id": "20261124-0001",
      "title": "提交实验报告",
      "due": "2026-12-04T23:59:00",
      "due_hint": null,
      "status": "pending",
      "notes": "逾期扣10分",
      "created_at": "2026-11-24T16:20:11",
      "updated_at": "2026-11-24T16:20:11",
      "completed_at": null,
      "source": "image",
      "ai": { "confidence": 0.86, "model": "qwen-vl-max", "raw_text": "第13周周五前提交" },
      "image_ref": "images/20261124-0001.png"
    }
  ],
  "settings": { "lead_times": ["1d", "1h"], "gentle": true }
}
```

字段约束：

| 字段 | 约束 |
| --- | --- |
| `status` | 仅 `pending` / `someday` / `done`；**不存 expired** |
| `due` | ISO 8601 或 `null`；`null` 就进待设时间区 |
| `due_hint` | 时间原始文字（"第13周周五"）；`due=null` 且来自图片时必填，用于在列表里给人工参照 |
| `source` | `image` / `manual`，用于文档里统计"AI 帮了多少" |
| `ai.confidence` | 0~1；`< 0.6` 的条目在确认框里标红提示「把握较低，请核对」，但**默认仍然勾选**——漏掉一条的代价大于多一条 |
| `image_ref` | 相对路径，原图保留供事后核对（可配置开关） |

### 5.4 图片解析流程

```
① 预处理：等比缩放到长边 ≤ 1600px，转 RGB，压缩到 ≤ 1.5MB
② 调用模型：system prompt 约束"只输出 JSON 数组"
③ 结构校验：字段类型 / 时间可解析 / 标题非空
④ 时间归一化：**模型只负责照抄原文**，日期换算全部在本地 `rules.resolve_text_due` 里做（纯函数、可单测），规则：
   - 只写月日（"12/1""1月5日"）→ 先按**今年**算；今年的那一天**已经过去了就顺延到明年**（学期跨年很常见：11 月贴出的"1月5日"指的是明年 1 月）
   - 写星期（"周五""下周三"）→ 取**最近的下一个**该星期几；今天就是它、且钟点未过则取今天；已经过了就往后推到下周的同一天
   - 只给日期不给钟点 → 补 **23:59**（这些表述都是「截止」语义，不是开始时间）
   - 涉及"第 N 周 / 周次"的表述**不做换算**，`due` 置 `null`，原文写入 `due_hint`，由人工设定〔已定〕
   - 原文写了四位年份（"2027年3月2日"）→ 原样尊重，不做任何漂移
⑤ 置信度提示：< 0.6 的条目在确认框里标红「把握较低，请核对」，但不替用户决定丢弃（实测模型对"第13周"这类条目会给出 0.5~0.6 的把握，若默认不勾选，用户一路"全部加入"就会把它静默丢掉）
⑥ 进草稿：用户勾选采纳 → 写库
```

**失败与降级**（这一段决定产品能不能演示）

| 失败情形 | 处理 |
| --- | --- |
| 没配 API Key | 上传按钮旁提示"未配置 AI 接口，可手动录入"，不阻塞主功能 |
| 网络超时（15s） | 提示"识别超时，已保留图片，可手动填写"，图片不丢 |
| 返回非 JSON | 重试一次（加严 prompt），仍失败则降级为"把模型原文贴给用户，手动整理" |
| 时间解析失败 | 该条 `due=null` → **自动落入待设时间区**（恰好是产品既定规则，不是特例） |
| 时间是"第 13 周周五"这类周次表述 | **不换算**，`due=null`、`due_hint="第 13 周周五"` → 落入待设时间区并显示原文，由人工补日期〔已定〕 |
| 只有月日、没写年份 | 按今年算；**今年已过则算明年**（实测："1月5日"在 11 月识别为 2027-01-05，而不是早已过去的 2026-01-05） |
| 图片中无日程 | 明确提示"未识别到时间信息"，不生成空条目 |

> 第 4 条是设计上的巧劲：**用产品规则兜住 AI 的不确定性**，而不是假装 100% 准。识别不出时间 → 置顶高亮让用户补，体验上完全自洽。

### 5.5 关键 Prompt 草案

```
system:
你是日程信息抽取器。只输出 JSON 数组，不要任何解释文字。
每个元素字段：
  title        string  日程标题，动宾结构，≤20字
  due_hint     string  图上关于时间的原文，一字不改地照抄（如"12月8日上午9:00""下周三之前""第13周周五23:59"）
  due          string  仅当你确定完整的"年-月-日"时才填 ISO8601；只写了月日、星期、周次的填 null
  notes        string  附加要求（如"逾期扣分""需带学生证"），无则 ""
  confidence   number  0~1，你对 due 这个字段的把握
规则：
  - 一张图里若有多个时间节点，拆成多条
  - 时间原文必须完整出现在 due_hint 里，不要自己补年份、不要改写成日期
  - 图上没写年份就不要编年份；只写"第N周"的不要自己推算日期
  - 不要编造图中不存在的信息

user:
[图片]
```

> 故意不给模型学期周历：周次换算一旦猜错就是错误的截止时间，比"留空等人填"危害大得多。
> 而"月日 / 星期"这类能算准的，也**不交给模型算**——放本地按固定规则算，换模型、换版本结果都一样，
> 还能写单元测试钉死（见 `tests/test_rules.py::TestResolveText`）。

### 5.7 AI 接口配置（人工输入）

接口信息**不写死在代码里，也不读环境变量**——全部由用户在设置面板里手工填写，保存到本地 `data.json` 的 `ai` 段。理由很实际：演示机上不会有环境变量，评委一定会问"Key 从哪来"；而把 Key 写进代码，一提交到 GitHub 就是泄露。

```
┌──────────────────────────────────────────────────┐
│ 设置 · AI 接口                                   │
├──────────────────────────────────────────────────┤
│ 接口地址  [ https://dashscope.aliyuncs.com/…  ]  │
│ 模型名    [ qwen3-vl-plus                     ]  │
│ API Key   [ ••••••••••••••••••••  ]  [显示]      │
│                                                  │
│ 状态：● 未配置 / ● 连通，模型能读图（1.4s）      │
│       / ● 接口通了，但模型对图片返回空…          │
│                        [测试连接]  [取消] [保存] │
└──────────────────────────────────────────────────┘
```

| 行为 | 规则 |
| --- | --- |
| 保存 | 写入 `data.json` 的 `ai` 段；Key 明文存本地，不加密（本机单人使用，加密带来的复杂度大于收益） |
| 掩码 | 输入框默认显示 `•`，点「显示」临时切换 |
| 测试连接 | **发一张写着 42 的 96×56 小图**，要求模型复述数字，20s 超时。只用 1×1 像素 ping 测不出"模型不支持看图"——纯文本模型会直接忽略图片、照样回一句"ok"，看起来一切正常，直到真传截图才返回空数组（本项目实际踩过） |
| 未配置时 | 「上传图片」置灰，悬停提示"请先在设置里填写 AI 接口"；**手动录入完全不受影响** |
| 错误码映射 | 401/403 → "Key 无效或权限不足"；404 → "接口地址或模型名不对"；超时 → "网络不通或超时" |
| 切换供应商 | 只要兼容 OpenAI Chat Completions 格式，改 Base URL + 模型名即可，无需改代码 |

**模型必须能看图**。实测同一网关下：

| 模型 | 读图自检 | 一张 4 条通知截图的抽取 | 耗时 |
| --- | --- | --- | --- |
| `qwen3-vl-plus` | 通过 | 4/4，标题完整（"完成课程设计选题并提交组队名单"） | 7.2s |
| `qwen3.7-flash` | 通过 | 4/4，标题略被截短（"完成课程设计选题"） | 17.2s |
| `deepseek-v4-flash-0731` | **失败**（返回空） | 0 条 | — |

### 5.8 开源复用与许可证核查

写代码前先去 GitHub 找现成的，别重复造轮子；但**许可证不兼容的一律不碰**。完整清单见 `CREDITS.md`，这里记结论：

| 候选 | 许可证 | 处理 |
| --- | --- | --- |
| [`bmjcode/tkScrolledFrame`](https://github.com/bmjcode/tkScrolledFrame) | MIT | **采纳**：滚轮事件按控件逐个绑定（避免 `bind_all` 在弹窗里误滚动），跨平台 delta 处理，改写约 15 行并在 `app.py` 注明出处 |
| [`CustomTkinter`](https://github.com/TomSchimansky/CustomTkinter) ★13.6k | MIT | 不采纳：圆角主题好看但要 `pip install`，与"双击即跑"冲突，列为后续可选项 |
| [`j4321/tkcalendar`](https://github.com/j4321/tkcalendar) | **GPL-3.0** | **拒绝**：传染性协议，链接进来等于整个项目被迫 GPL；改为**自绘月历** `datepicker.py`（约 380 行，零依赖） |
| [`sumqwerty/tkinter-scrollable-frames`](https://github.com/sumqwerty/tkinter-scrollable-frames) | **GPL-3.0** | 拒绝，同上 |

三条硬规矩：

1. 只引入 **MIT / Apache-2.0 / BSD** 这类宽松协议；GPL、AGPL 一律不用。
2. 每处借鉴都要在源码里写明出处与改了什么，不许"看起来像自己写的"。
3. 能只借思路就不复制整文件；复制了就必须留 LICENSE 声明。

### 5.8 截止时间用日历选，不用文本框〔已定 · 2026-11-24〕

最早的版本是文本框 + 多格式解析（`2026-12-04 23:59` / `12-04 23:59` / `23:59`）。放弃它的理由不是做不出来，而是**它把格式的负担丢给了用户**：

| 文本输入的问题 | 日历选择的处理 |
| --- | --- |
| 打错一个字就整条保存失败，还要读错误提示 | 不可能输错，选中的就是存下的 |
| 想设"下周三"得自己算日期，跨月还算错 | 翻一页就能点 |
| 时分要手打，`9:00` 与 `09:00` 得兼容 | 上下箭头 + 四个常用时刻快捷键（09:00 / 14:00 / 18:00 / 23:59） |
| 手机上早已是选择式，回到文本框是倒退 | 与系统日历同一套心智 |

实现是自绘的 `datepicker.py`（周一起始、6 行 36 格、跨月灰显、今天带浅绿底、选中填绿），不依赖 `tkcalendar` 的 GPL。

交互约定：

- 点字段 → 弹月历（贴着字段下方，下方放不下自动翻到上方）
- 点日期只改选中的那天，浮层不关；点「确定」才提交，双击某天等于"选它并确定"
- 「清除」= 清掉时间，条目随后进「待设时间」区；「今天」= 回到本月并置为今天 18:00
- 未设置时间的字段显示灰字「未设置 · 点此选择」，不是空白——空白无法判断是"没填"还是"控件坏了"
- 新增条目时**不预勾**"不设时间"，默认就能点开日历；编辑已有条目则跟随它当前有没有时间

## 6. 创新点与价值
| # | 创新点 | 为什么算创新（不是包装） |
| --- | --- | --- |
| 1 | **状态即位置**：不靠标签和筛选器，用"在哪个区"表达状态 | 零学习成本，用户不用理解"优先级/标签/过滤器"这套概念；也天然规避了 tkinter 做复杂筛选 UI 的成本 |
| 2 | **"没时间"不是错误，是一种正式状态** | 主流待办都把缺字段当异常；这里把它升格为置顶高亮区，把 AI 的不确定性转化成产品的引导动作 |
| 3 | **不确定性外显**：`due` 抽不出来不硬猜，转成"待设时间 + 原文提示"；置信度 <0.6 的条目标红提醒但仍默认勾选 | 不假装准确，把判断权交回人手里，也不替人做丢弃决定；正好对上大赛"AI 使用规范"的评审口味 |
| 4 | **规则层可单测**：`bucket()` 是纯函数 | 让"排序对不对"变成可验证的断言，而不是靠肉眼点五分钟 |
| 5 | **零依赖分发**：除 Pillow 外全标准库 | 评委或同学拿到文件夹双击就能跑，不需要 pip install |

**价值**：把一个每天发生 3~8 次、每次 30 秒的手工动作压到 3 秒，一年省下约 40 小时；且降低"漏掉截止时间"的隐性代价。

## 7. AI 开发规则（团队约定 + 大赛合规）

> 这一节同时是给团队用的工作手册，也是大赛「学术诚信与 AI 使用规范」（12.5%）那一项的答题素材。原则只有一句：**AI 负责产出候选方案，人负责定义问题、做取舍、签字验收。**

### 7.1 五条铁律

1. **AI 不定义需求**。需求由人写下来（本文件第 4 节就是范例），AI 只能对已写下的需求提改进建议。
2. **AI 不签字验收**。任何"能用/不能用"的结论由人跑一遍界面后写出，不由模型自述。
3. **每一次 AI 参与都留痕**。没有 Prompt 记录的产出，视为未发生，不进最终代码。
4. **不把密钥、个人信息、他人代码喂给 AI**。截图里的姓名学号在送入模型前要打码或裁剪。
5. **不整段照抄**。AI 生成的代码必须能解释每一行为什么这么写，讲不清就重写。

### 7.2 分工边界表

| 环节 | 交给 AI | 人必须做 | 留痕方式 |
| --- | --- | --- | --- |
| 需求分析 | 梳理场景、补漏掉的边界情况 | 决定做什么、不做什么（第 2.3 节） | `docs/需求-YYYYMMDD.md` |
| 界面设计 | 给 3 版线框文字描述、配色建议 | 选定一版并说明理由 | `docs/design-decisions.md` |
| 编码实现 | 生成函数级代码、写 tkinter 布局 | 逐段读懂、改成自己的命名与结构 | `prompts/` + commit message |
| 调试修复 | 读报错、给候选原因、给补丁 | 复现问题、验证补丁真的修好了 | `docs/bugs.md`（现象/原因/改法） |
| 测试 | 生成边界用例列表 | 真的跑一遍，记录实际结果 | `docs/test-log.md`（用例/预期/实际/结论） |
| 文档整理 | 起草章节、润色表达 | 核对事实、删掉没做过的功能 | 文档末尾 AI 使用附录 |

### 7.3 Prompt 存档规范

- 目录：`prompts/`
- 命名：`YYYYMMDD-序号-用途.md`，例：`20261125-01-排序规则实现.md`
- 每条记录固定五段：

```markdown
## 目标
（这次想让 AI 干什么，一句话）

## 上下文
（贴了什么文件/报错/需求原文）

## Prompt
（完整原文，不改写、不美化）

## 输出摘要
（AI 给了什么，几版候选，各自特点）

## 采纳与修改
（用了哪一版、我改了哪里、为什么改）
```

> 第 5 段是最值钱的部分。评审看的不是"你会不会问 AI"，而是"你能不能判断 AI 给的东西对不对"。

### 7.4 迭代记录

- 文件：`docs/ai-changelog.md`，**只追加不覆盖**
- 每次有效迭代记一行：`日期 | 环节 | 改了什么 | 触发原因（测试失败/体验差/评审意见） | 结果`
- 目的：让"迭代优化"这一项有证据链，而不是文档里一句"经过多次优化"

### 7.5 人工核查清单（每次提交前逐项过）

- [ ] 程序在**干净目录**双击能启动（不依赖我本机的绝对路径）
- [ ] 代码里没有硬编码的 API Key、用户名、盘符路径
- [ ] `bucket()` 的边界用例全过：无时间 / 刚过期 / 正好到点 / 已完成 / 不急
- [ ] 关闭窗口 → 托盘图标在 → 单击能唤回；托盘不可用时降级为最小化
- [ ] `data.json` 写入后立刻断电式关闭，重开数据不丢（原子写入验证）
- [ ] 断网状态下点"上传图片"，给出的是可理解的提示，不是报错堆栈
- [ ] 图片里的个人信息已打码/裁剪，本地 `images/` 目录不误提交
- [ ] 文档里写的每个功能，界面上都真的能点到

### 7.6 禁止清单

| 禁止 | 原因 |
| --- | --- |
| 用 AI 生成测试结论、编造运行截图 | 学术诚信红线，一票否决级别 |
| 把含他人姓名学号的截图上传到公网模型 | 隐私与数据安全 |
| 直接粘贴 AI 生成的整段代码而不理解 | 无法应对答辩追问，且埋 bug |
| 引用他人项目/开源代码不注明 | 抄袭 |
| 让 AI 代写整篇项目文档后直接提交 | 文档要能反映团队真实理解 |

### 7.7 数据与隐私

- 日程数据**只存本地** `data.json`，不上传任何服务器
- 调用多模态接口时只发**图片本身 + 最小必要提示词**，不发本地日程内容
- 原图默认保留在 `images/`（供核对），设置里可关闭；`images/` 与 `data.json` 加入 `.gitignore`
- 文档中展示的截图，姓名/学号/手机号一律打码，并注明"已脱敏"

### 7.8 学术诚信与署名

- 代码仓库保留真实提交记录，不 squash 掉 AI 辅助过程
- 项目文档末尾附「AI 工具使用说明」：工具名、使用环节、生成内容范围、人工修改比例、核查方式
- 第三方素材（图标、字体、示例图片）注明来源与授权

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 多模态识别不准（尤其手写、复杂课表） | 演示翻车 | 演示用打印体截图；识别失败自动落"待设时间区"，把失败变成流程的一环 |
| API 无网络 / 无额度 | 现场不能演示 | 准备离线降级模式（手动录入全功能可用）+ 录屏兜底 |
| tkinter 动画卡顿 | 观感差 | 动画全部走 `after()` 分帧，不做阻塞循环；单行动画 ≤ 500ms |
| 中文路径 / 打包问题 | 换机器跑不起来 | 全程 `pathlib`，文件名不用中文；启动脚本不写死绝对路径（吸取 `喝水提醒` 的教训） |
| 团队合并时规则冲突 | 返工 | 本稿第 4.2 节作为"规则唯一来源"，合并时以行为描述为准而非代码 |
| 时间不够 | 交付残缺 | 优先级：手动录入 + 分区 + 打勾 > 图片识别 > 提醒 > 托盘 |

| 4 | AI 接口怎么配 | **设置面板人工输入**（地址/模型/Key），存本地 `config.json`，带测试连接 | 4.5 / 5.7 |

> 第 3 条的取舍值得记一笔：省掉周历换算能少一个 bug 源，代价是用户要多点一次「设置时间」。但错误的截止时间比空着的截止时间危害大得多，所以宁可留空。

**本轮发现并修掉的问题**（3 个）

1. **顶栏溢出**：760px 窗口下顶栏实际需要 787px，「上传图片」被挤出窗口。统计文字独立成第二行后需求宽度降到 453px。
2. **纯文本模型静默失败**：旧"测试连接"只发 1×1 像素 + "ping"，纯文本模型忽略图片照样回 "ok"，界面显示"连通"，真传截图却永远返回 0 条。改为发写着 42 的小图做读图自检，把"接口通了"和"模型会看图"分开报。
3. **低置信度条目被静默丢弃**：旧逻辑 `confidence < 0.6` 默认不勾选。实测模型对"第13周周五"这类条目会给 0.55 的把握，用户一路"全部加入"就会把它漏掉。改为全部默认勾选 + 标红提示。
